Как получить по-настоящему случайное число и где на этом ошибаются. Тема всплыла из разбора чужого покера, но нужна шире: перемешивание колоды, токены сессий, коды подтверждения, пароли, ссылки для сброса пароля — везде, где предсказуемость означает дыру. Для трека C это ещё и содержание шагов `c-slot` и `c-compliance`.

> **Короткий ответ.** `Math.random()` — никогда там, где предсказуемость чем-то грозит. Берите `crypto.randomInt()` в Node и `crypto.getRandomValues()` в браузере, перемешивайте Фишером–Йетсом, а диапазон сужайте отбрасыванием хвоста, а не остатком от деления.

## Три уровня случайности

### Псевдослучайный генератор

`Math.random()` в V8 — это xorshift128+: детерминированный алгоритм, который гонит поток чисел из внутреннего состояния. Одинаковое состояние даёт одинаковый поток, а само состояние восстанавливается по нескольким выданным значениям — вместе со всей дальнейшей последовательностью.

Для анимации, выбора случайной подсказки, тасовки учебной колоды — нормально. Для денег, токенов и паролей — нет.

Отдельно: **сид у `Math.random()` задать нельзя.** Если нужна воспроизводимость, берут свой маленький ГСЧ вроде mulberry32 — пять строк, и одинаковый сид даёт одинаковый результат. Это удобно в тестах: упавшую раздачу можно повторить.

### Криптостойкий генератор

То, что на практике и называют «настоящим». Числа берутся из энтропийного пула ядра, а пул наполняется с железа: тайминги прерываний, шум на входах, инструкции процессора `RDSEED`. Предсказать следующее значение нельзя, даже зная все предыдущие.

```js
// Node
import { randomInt, randomBytes, randomUUID } from 'node:crypto'
randomInt(52)          // 0..51 равномерно
randomBytes(32)         // 32 случайных байта — на токен
randomUUID()            // идентификатор

// браузер
crypto.getRandomValues(new Uint32Array(1))
crypto.randomUUID()
```

Стоит это дороже `Math.random()`, но разница заметна только если дёргать миллионы раз в секунду. Колода из 52 карт — 51 вызов на раздачу.

### Аппаратный источник

`/dev/random`, отдельные чипы, квантовые генераторы. Напрямую к ним почти никогда не обращаются: операционная система уже смешала их в свой пул, и брать оттуда правильнее, чем городить свой доступ к железу.

## Ловушка, на которой спотыкаются чаще, чем на самом генераторе

Генератор взяли правильный, диапазон сузили неправильно:

```js
randomBytes(1)[0] % 52
```

Байт даёт 0–255. Делим с остатком на 52: значения 0–47 выпадают по пять раз, 48–51 — по четыре. Перекос примерно четверть. В колоде это значит, что одни карты приходят чаще других.

Ошибка тихая: тесты проходят, глазами не видно, ловится только подсчётом распределения на большом прогоне.

**Лечится отбрасыванием хвоста.** Берём только ту часть диапазона, которая делится нацело, остальное перетягиваем:

```js
function randomBelow(max) {
  const range = 2 ** 32
  const limit = range - (range % max)   // хвост, который портит равномерность
  const buf = new Uint32Array(1)
  let value
  do {
    crypto.getRandomValues(buf)
    value = buf[0]
  } while (value >= limit)              // выпало в хвост — тянем заново
  return value % max
}
```

Цикл почти никогда не делает второго круга: хвост мал относительно диапазона.

В Node это уже сделано за вас — `crypto.randomInt(max)` внутри работает именно так. Поэтому его и берут вместо ручной арифметики с байтами.

## Перемешивание

Источник — половина дела. Вторая половина — алгоритм.

```js
function shuffle(items, rnd) {
  for (let i = items.length - 1; i > 0; i -= 1) {
    const j = rnd(i + 1)                        // из ОСТАВШИХСЯ, не из всех
    ;[items[i], items[j]] = [items[j], items[i]]
  }
  return items
}
```

Это Фишер–Йетс: идём с конца и меняем текущий элемент со случайным из ещё не разобранных. Каждая из 52! перестановок равновероятна.

Две ошибки рядом с ним:

**Наивный шаффл.** Если написать `rnd(items.length)` вместо `rnd(i + 1)` — то есть менять со случайным из всех, а не из оставшихся, — распределение перекашивается. Разница в коде одна скобка, в результате принципиальная.

**Сортировка случайным компаратором.**

```js
array.sort(() => Math.random() - 0.5)   // не перемешивание
```

Выглядит убедительно и не работает. `sort` требует последовательного компаратора: если при сравнении `a` и `b` ответ был «меньше», при повторном сравнении он обязан быть тем же. Здесь ответ случайный каждый раз, поэтому алгоритм сортировки ведёт себя непредсказуемо, а часть перестановок выпадает заметно чаще других. Конкретный перекос зависит от того, какую сортировку использует движок, — то есть результат ещё и разный в разных браузерах.

Это классический вопрос на собеседовании. Встречается в живом коде постоянно.

## Для iGaming обычного криптогенератора мало

Там нужен не просто честный генератор, а **доказуемо честный**: игрок должен убедиться сам, не веря оператору на слово. Схема называется provably fair и устроена так:

1. Сервер придумывает секрет и публикует его **хеш** до начала раздачи.
2. Игрок присылает свой seed — любой, хоть случайный.
3. Исход раунда считается детерминированно: `HMAC-SHA256(секрет, клиентский seed + номер раунда)`, а из полученных байтов уже берутся числа.
4. После раунда сервер раскрывает секрет. Игрок проверяет, что хеш сходится, и пересчитывает исход сам.

Подменить результат задним числом нельзя: хеш опубликован раньше, чем стали известны карты. Повлиять только со своей стороны тоже нельзя — в расчёт входят оба seed.

Плюс требование сертификации: **генератор держат отдельным заменяемым модулем**, потому что лаборатория проверяет именно его, а версия сборки пишется в журнал каждого раунда — иначе непонятно, какой код считал деньги.

## Что взять в работу

| Задача | Чем брать |
|---|---|
| Анимация, случайная подсказка, учебный пример | `Math.random()` |
| Воспроизводимость в тестах | свой ГСЧ с сидом, например mulberry32 |
| Токен, код подтверждения, ссылка сброса пароля | `crypto.randomBytes` / `randomUUID` |
| Колода, лотерея, любой розыгрыш на деньги | `crypto.randomInt` плюс Фишер–Йетс |
| Игра под сертификацию | provably fair поверх криптогенератора |

В вашем `Online-poker` алгоритм уже правильный — Фишер–Йетс, — а источник по умолчанию `Math.random()`, и сид оставлен намеренно: на нём держатся тесты и воспроизводимость упавшей раздачи. Правильная конфигурация для боевого режима: `crypto.randomInt` по умолчанию, сид подставляется явно только в тестах.
