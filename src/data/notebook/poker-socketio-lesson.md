Разбор чужого проекта `intfloatbol-poker-websocket-client-server` — холдем на Node, TypeScript и Socket.IO, около 1200 строк. Читать его полезно не как образец для копирования, а как готовый материал к шагу `b-socketio`: там разобраны WebSockets, а здесь видно, во что они превращаются в живой игре. Рядом лежит ваш собственный `Online-poker`, написанный на те же задачи по-другому, — сравнение двух решений учит быстрее, чем любой из них по отдельности.

## Как проходит одна раздача

Сервер ждёт, пока зарегистрируются двое, и вызывает `PokerGame.RunAsync`. Дальше всё крутится в цикле «раздача за раздачей», пока у кого-то не кончатся фишки.

Самое интересное место — как описана сама раздача:

```ts
const streets = [
  () => this.PreflopAsync(players),
  () => this.FlopAsync(players, deck, tableCards),
  () => this.TurnAsync(players, deck, tableCards),
  () => this.RiverAsync(players, deck, tableCards),
  () => this.ShowdownAsync(players, tableCards),
]

for (const street of streets) {
  const streetWinner = await street()
  if (streetWinner != null) { /* забрал банк, раздача кончилась */ break }
}
```

**Это стоит запомнить.** Линейный сценарий описан списком шагов, а не `switch` по состоянию игры. Читается сверху вниз как сюжет: префлоп, флоп, тёрн, ривер, вскрытие. Если на какой-то улице кто-то сфолдил — функция возвращает победителя, цикл обрывается.

Приём хороший там, где сценарий действительно линейный и один. Ограничение всплывает сразу за этим.

## Главное архитектурное решение: сервер ждёт игрока

Внутри улицы происходит вот что:

```ts
const playerAction = await player.MakeActionAsync(possibleActions)
```

Сервер буквально **останавливается** и ждёт, пока игрок пришлёт ход. Промис разрешится, когда придёт сообщение по сокету.

Плюс очевиден: код читается как обычная последовательная программа, никаких машин состояний. Для учебного проекта на двоих это самое понятное решение, какое можно выбрать.

А теперь минусы, и они и есть урок:

- **Один стол на процесс.** Пока сервер висит в `await`, он не может вести вторую игру.
- **Нет таймаута на ход.** Игрок ушёл пить чай — раздача стоит вечно.
- **Отключение посреди хода.** `HandlePlayerDisconnect` удаляет игрока из карты, но промис в `MakeActionAsync` никто не разрешает: игра остаётся висеть.
- **Состояние живёт в стеке вызовов**, а не в объекте. Его нельзя сохранить, восстановить или показать целиком.

В вашем `Online-poker` та же задача решена наоборот: есть объект `Table` с полями `street`, `toAct`, `pot`, и метод `act()` — обычный синхронный вызов, который меняет состояние и сразу возвращается. Сервер ничего не ждёт: пришло событие — применили, разослали новое состояние. Поэтому там один процесс может вести сколько угодно столов, тест может проиграть партию без сокетов, а отключившийся игрок просто фолдит.

**Вывод для собеседования:** «сервер ждёт игрока» и «сервер хранит состояние и реагирует на события» — это два разных способа писать многопользовательскую игру. Первый проще читать, второй масштабируется. Уметь назвать разницу важнее, чем знать Socket.IO.

## Состояние клиента на RxJS

`PlayerStats` — десять полей, и каждое отдельный `BehaviorSubject`:

```ts
public TotalBank: BehaviorSubject<number>
public Hand: BehaviorSubject<string[]>
public EnemyBank: BehaviorSubject<number>
// …ещё семь
```

Дальше `combineLatest` на все десять: как только меняется любое, собирается и уходит клиенту весь снимок.

Идея правильная — клиент не запрашивает состояние, а подписан на него. Но цена видна в коде: синхронизировать `EnemyBank` и `EnemyBet` приходится руками, и делается это в четырёх разных местах `PokerGame`:

```ts
players.forEach(p => {
  const enemy = this.GetPlayerExcluded(players, p)
  p.EnemyBet = enemy.CurrentBet
  p.EnemyBank = enemy.TotalBank
})
```

Каждый раз, когда что-то меняется, автор вспоминает продублировать это сопернику. Забыл в одном месте — у клиента устаревшая цифра.

Альтернатива, которую стоит держать в голове: **одно состояние и функция-проекция.** Держать один объект стола, а клиенту отдавать `viewFor(id)` — срез, где чужие карты вырезаны. Тогда синхронизировать нечего: поле одно, а видов столько, сколько зрителей. Именно так сделано в вашем репозитории.

## Три места, где стоит остановиться

### Перемешивание сломано

```ts
export function ShuffleArray<T>(array: T[]) {
  return array.sort(() => Math.random() - 0.5)
}
```

Выглядит убедительно и **не работает.** `sort` требует последовательного компаратора: если `a < b`, то при повторном сравнении ответ должен быть тем же. Здесь он случайный каждый раз, поэтому алгоритм сортировки ведёт себя непредсказуемо, а распределение получается неравномерным — некоторые перестановки выпадают заметно чаще других. В покере это буквально предсказуемость карт.

Правильный способ — Фишер–Йетс: идти с конца массива и менять текущий элемент со случайным из оставшихся. Пять строк.

Это классический вопрос на собеседовании, и хорошо, что вы увидели ошибку в живом коде, а не в статье.

### Ставки только «в три раза»

Произвольного рейза нет. Есть `TRI_BET` — ставка ровно втрое от текущей максимальной, и она доступна, только если `TotalBank > maxBet * 3`.

Упрощение сознательное, но из него выпадает то, что в настоящем покере создаёт всю сложность торговли: минимальный рейз, повторное открытие торговли после рейза, короткий олл-ин меньше минимума. В вашем варианте это есть — и именно этот кусок было писать труднее всего.

### Конец торговли определяется равенством ставок

```ts
IsAllBetsEqual(): boolean {
  return this._players.every(p => p.CurrentBet === this._players[0].CurrentBet)
}
```

Круг опрашивает обоих игроков подряд, потом проверяет равенство. Из-за этого игрока могут спросить ещё раз, когда ставки уже сравнялись, — безвредно, но лишний вопрос.

Надёжнее считать не равенство сумм, а **кто ещё не отвечал на последний рейз**. Тогда правило одно: торговля закрыта, когда все живые игроки походили после последнего повышения и уравняли ставку.

## Что в этом проекте сделано хорошо

Честно, не всё плохо — иначе разбирать было бы нечего.

**Оценка комбинаций отдана библиотеке.** `Hand.solve([...hand, ...table])` и `Hand.winners(hands)` из `pokersolver`. Для продукта это правильное решение: не писать своё там, где есть проверенное. Обратная сторона — вы не узнаете, как это устроено, а спрашивают именно это. Поэтому в вашем репозитории оценка своя, на сто тридцать строк, и покрыта тестами.

**Регистрация через колбэк Socket.IO.** Клиент шлёт `register-player-req` и получает ответ прямо в колбэк:

```ts
callback({ success: false, error: 'cannot register player…' })
```

Это редко кто использует, а вещь полезная: запрос-ответ поверх событийного транспорта, без придумывания своих `*-response` событий.

**События вынесены в константы.** `SocketPokerEventNames` вместо строк по коду — опечатку в имени события иначе ловить мучительно, потому что оно просто молча не сработает.
